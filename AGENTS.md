# Инструкции для работы с монорепозиторием

## Назначение и карта проекта

DIO AI Courses — платформа учебных курсов с AI-генерацией, практикой,
тестированием, организациями, участниками и приглашениями.

- `backend/` — Python API, бизнес-логика, AI, фоновые задачи и интеграции.
- `frontend/` — React SPA (JS/JSX): обучение, создание курсов и управление.
- `docker/`, `docker-compose.yml` — контейнеры; `monitoring/` — метрики/логи/дашборды.
- `nginx/` — CDN; `frontend/nginx.conf` — SPA и API/storage proxy.
- `scripts/`, `Makefile` — backup/restore, не проверки качества.

SPA использует REST JSON `/api/v1` и polling генерации; uploads описаны ниже.
Backend работает с PostgreSQL, Redis, RabbitMQ, Qdrant и S3-совместимым RustFS.
Некоторые межмодульные взаимодействия — HTTP, несмотря на общий репозиторий.

## Иерархия инструкций

- Этот файл действует во всём репозитории; при работе с Backend обязательно учитывай
  `backend/AGENTS.md`, с Frontend — содержательные `frontend/AGENTS.md` и вложенные инструкции.
- Локальные правила уточняют общие в своей области и при конфликте проектных правил имеют
  приоритет; они не обходят системные инструкции, запрос пользователя и ограничения инструментов.
- Не полагайся на одинаковую автозагрузку: Codex собирает цепочку до рабочей директории,
  с `AGENTS.override.md` и лимитом `project_doc_max_bytes`; Zed использует свой загрузчик,
  внешние агенты — собственный. Не загруженный специализированный файл прочитай явно.
- README и тесты могут содержать устаревшие контракты; сверяй их с кодом.
  Пути в этом файле — от корня репозитория; `/api`, `/assets` и подобные — URL-пути.

## Исследование перед изменениями

1. Определи затронутые модули; прочитай реализацию, ближайшие тесты и аналогичный сценарий.
2. Проследи вызывающий код, DI, конфигурацию, контракты, сериализацию и проверки доступа.
3. Оцени последствия для потребителей, данных, фоновых задач и повторного выполнения.

Глубина исследования соразмерна задаче: локальная правка не требует обхода всего репозитория.
Сначала проверь рабочее дерево; не перезаписывай пользовательские изменения/untracked-файлы
и не восстанавливай удаления без разрешения.

## Общие инженерные правила и границы изменений

- Переиспользуй архитектуру, helpers и зависимости модуля; не дублируй функциональность.
- Новые абстракции/библиотеки обоснуй; сохраняй согласованность manifest/lockfile.
- Сохраняй границы и совместимость, если задача не требует иного. Не меняй соседние модули,
  инфраструктуру, API/имена и архитектурные слои вне задачи.
- Не удаляй тесты и не ослабляй проверки ради зелёного результата.
- Посторонние дефекты сообщай отдельно, не исправляй их попутно.

## Согласованность Backend и Frontend

- Клиенты: `frontend/src/utils/api.js`, `frontend/src/utils/attachments.js`,
  `frontend/src/services/theorySessionApi.js`; проследи потребляющие stores/hooks/components.
- API base — `/api/v1`, не `VITE_API_URL`; Vite dev proxy покрывает только `/api`.
- Согласовывай имена полей, nullability, enum, пагинацию, статусы HTTP и пустые ответы/204.
  Frontend преобразует snake_case/camelCase и API-модули в UI-блоки; учитывай эти mapper'ы.
- Сохраняй login → authentication token → выбор membership → access/refresh → identity.
  UI guards и `PermissionGate` не заменяют серверную проверку прав на ресурс.
- Проверяй совместимость ошибок с `ApiError`: используются `error`, `detail` и validation 422.
- Не заменяй JSON/polling генерации на SSE вне задачи; SSE Backend относится к уведомлениям.
- Media attachments: presigned URL → прямой PUT → confirm, клиент —
  `frontend/src/utils/attachments.js`; документы и файлы практики — multipart через
  `frontend/src/utils/api.js`. Не переноси механизм одного сценария на другой автоматически.
- Для media сверяй DTO/routes в `backend/src/media/` с клиентом: текущие формы расходятся,
  описание workflow не гарантирует совместимость payload. Не отправляй API Bearer на storage;
  сохраняй обязательные upload headers, проверяй ключи, URL и proxy Host.
- Лимиты сверяй между UI, API и `frontend/nginx.conf`: proxy может отклонить запрос раньше API;
  клиентская валидация не защищает сервер. Обновляй только затронутые контракты и проверки.

## Безопасность и эксплуатационные ограничения

- Не раскрывай реальные секреты, API-ключи, JWT, пароли и presigned URL в коде/логах/отчётах;
  явно синтетические fixtures допустимы. Не открывай `.env*` без необходимости.
- `VITE_*` попадает в клиентскую сборку: это не место для секретов.
- SPA хранит сессию в localStorage, не HttpOnly-cookie. Не расширяй хранение/логирование токенов;
  схему auth меняй только по задаче, без повторного согласования уже разрешённой работы.
- Пользовательский и LLM-контент недоверен. Сохраняй strict/sanitization Mermaid и проверки файлов.
- Не предполагай приватность S3-объектов: initializer RustFS устанавливает public GetObject.
  CDN `/assets/` использует длительное публичное immutable-кеширование.
- LLM-трейсы/Grafana содержат prompts/responses и персональные данные: не расширяй доступ
  или внешнюю отправку без оценки последствий.
- Не запускай приложения, worker, seed/debug-скрипты и Compose как безусловно безопасную проверку:
  startup Backend выполняет миграции/bootstrap, а корневой Compose включает Taskiq worker.
- Include `docker/services.docker-compose.yml` закомментирован: корневой Compose не запускает все приложения.
- Не запускай `make restore`/`scripts/restore.sh` для диагностики: они удаляют/меняют данные;
  backup/restore ещё опирается на старый MinIO, не текущий RustFS.

## Проверка изменений

- При изменении поведения добавь/обнови regression tests; начинай с целевых проверок.
  Если тест технически невозможен, объясни причину и предложи доступную альтернативу.
- Backend: команды, ограничения окружения и интеграционных тестов — в `backend/AGENTS.md`.
- Frontend: из `frontend/` — `npm run build` (создаёт `frontend/dist/`); при разрешённой
  и необходимой установке — `npm ci` по `frontend/package-lock.json`.
- Frontend: scripts `test`/`lint`/`typecheck` и TS config отсутствуют.
- В `.github/` только CODEOWNERS, не workflows; не обещай CI-проверки.
- Проверь diff на лишние изменения и совместимость API, доступа, сериализации и конфигурации.
- Не запускай проверки с внешними сервисами/платными LLM на рабочем окружении без согласования.
- Указывай команды и фактический результат; не называй чтение кода тестированием
  и не объявляй невыполненные проверки успешными.
