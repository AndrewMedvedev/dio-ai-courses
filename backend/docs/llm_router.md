# `llm_router`: маршрутизация LLM и учёт вызовов

Документ описывает **текущую реализацию**, а не предполагаемую архитектуру. Сведения из прежнего README перенесены сюда; устаревшие пути, маршруты и утверждение об отсутствии событий исправлены по коду. Исходный документ удалён после переноса. Модуль регистрирует модели в PostgreSQL, отправляет текст в Responses API, изображения — в Images API и публикует события мониторинга. Оркестрация tool loop, выполнение инструментов и предметная валидация результата находятся в [общем `llm_service`](../src/llm_service/services.py), не в роутере.

## Устройство и подключение

- HTTP-маршруты [моделей](../src/llm_router/api/v1/ai_models.py) и [ответов](../src/llm_router/api/v1/llm.py) подключаются через [автосборку API пакета](../src/llm_router/api/v1/__init__.py) к `/api/v1` в [`src/__init__.py`](../src/__init__.py). Там же импортируется [RabbitMQ consumer](../src/llm_router/infra/invocation_rabbit.py) ради регистрации подписки. `INSTALLED_MODULES` в [settings](../src/core/settings.py) не регистрирует HTTP.
- [DI репозиториев](../src/llm_router/api/dependencies/repos.py) создаёт `SqlAIModelRepository`/`SqlLLMInvocationRepository` на общей `DBSession`; [DI сервисов](../src/llm_router/api/dependencies/services.py) собирает text router с `ai_tunnel_client`, image router с дополнительным `proxy_api_client` и `MediaClient`, обоим даёт Redis-обёртку и event publisher. Сессия БД сама не коммитится; create/delete модели и consumer явно делают `commit`.
- [Сущности](../src/llm_router/domain/entities.py): `AIModel` (`name`, `complexity`, `description`, `context`, общий UUID/timestamps) и `LLMInvocation` (`request_id`, `model`, `total_tokens`, JSON request/response, `duration_ms`, `status`, `error`). [`Complexity`](../src/llm_router/domain/enums.py) — `easy`, `medium`, `hard`; статусы — `completed`/`failed`. [ORM](../src/llm_router/infra/models.py): `ai_models.name` уникален, `llm_invocations.request_id` индексирован, `total_tokens >= 0`. [SQL-репозиторий](../src/llm_router/infra/repository.py) преобразует entity/ORM и получает для маршрутизации только поля `name`, `complexity`, `description`, `context`.

## Реальные HTTP API

| Метод и путь                             | Ввод → результат                                                                                                                                                                              | Доступ и особенности                                                                                                                 |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /api/v1/ai-models`                 | JSON [`AIModelSchema`](../src/llm_router/application/schemas.py): обязательные `name: str`, `complexity: easy\|medium\|hard`, `description: str`, `context: int` → `201`, `AIModel`           | Глобальное `ai_model:create`; insert + commit; уникальность имени обеспечивается БД.                                                 |
| `POST /api/v1/ai-models/search`          | JSON [`Pagination`](../src/shared/application/dtos.py) `{ "page": 1, "size": 10 }` (по умолчанию; `size` до 100) → `200`, `Page[AIModel]` с `items`, `total`, `pages`, `has_next`, `has_prev` | Нужен `CurrentIdentity`; полный список сущностей, сортировка по `created_at` по убыванию. Это **POST с body**, не GET и не `/get`.   |
| `DELETE /api/v1/ai-models/{uid}`         | UUID в path → `204`, пустое тело                                                                                                                                                              | Глобальное `ai_model:delete`; SQL `DELETE` + commit. Отсутствующий UUID **не** вызывает 404 в текущем репозитории.                   |
| `POST /api/v1/responses/text?model=...`  | JSON [`LLMTextRequest`](../src/llm_service/schemas.py) → `200`, `LLMTextResponse`                                                                                                             | Нужен `CurrentIdentity`, отдельного permission нет; query `model` необязателен, но сейчас не используется как имя вызываемой модели. |
| `POST /api/v1/responses/image?model=...` | JSON `LLMImageRequest` → `200`, `LLMImageResponse`                                                                                                                                            | Нужен `CurrentIdentity`, отдельного permission нет; query `model` сейчас игнорируется.                                               |

Текстовый body: обязательная история — **список** словарей сообщений, не строка. DTO объявляет поле `messages` с алиасом `input` и принимает оба имени; [`LLMTextService`](../src/llm_service/services.py) фактически отправляет `messages`. Необязательные поля: `tools`, `instructions`, `reasoning` (`low`/`medium`/`high`), `temperature`, `text` (например `format.type=json_schema`), `disable_retries`, `final_tool_name`. `disable_retries` и `final_tool_name` — локальные управляющие поля и не пересылаются провайдеру. Результат содержит `messages` (история входа и выходные items), `tool_calls` (`call_id`, `name`, `arguments`, `arguments_error`), `raw_text`, `output` (dict при json_schema без tool calls), `total_tokens`. Схема — в [`llm_service/schemas.py`](../src/llm_service/schemas.py), разбор — в [`parse_response.py`](../src/llm_router/infra/parse_response.py).

Изображение: обязательная строка prompt — поле DTO `messages` с алиасом `prompt` (принимаются оба имени; сервис отправляет `messages`), опциональный `image` — список 1–5 строк, которые должны содержать base64-изображения; DTO проверяет длину списка, но не корректность base64, а ветка `images.edit` декодирует без `validate=True` ([схема](../src/llm_service/schemas.py), [роутер](../src/llm_router/application/llm_router.py)); поэтому для ошибочного base64 здесь нельзя обещать конкретный HTTP-статус. `quality` по умолчанию `medium`, `size` — `1024x1024`, `output_format` — `png`. Без `image` вызывается `images.generate`, с `image` — `images.edit` с декодированными байтами. В ответе `size`, `image`, `total_tokens`, `output_format`; фактически `image` **ключ сохранённого файла**, а не base64, несмотря на описание поля в схеме. Подробнее — [роутер](../src/llm_router/application/llm_router.py) и [учёт](../src/llm_router/application/track_invocation.py).

## Как выбирается модель

[`LLMTextRouter.call_llm`](../src/llm_router/application/llm_router.py) каждый раз читает первую страницу (`size=50`) `read_fields` через [`cache_ai_models`](../src/llm_router/infra/cache.py). Если query `model` **отсутствует**, отправляет сообщения, инструкции, tools и описание output на `https://api.aitunnel.ru/v1/decisions` с моделью классификатора `gpt-6-luna-decisions`; берёт `result["answers"]["complexity"]["choice"]`, фильтрует доступные модели по `complexity` и вызывает **первое** совпадение через `ai_tunnel_client.responses.create`. Если query `model` **передан**, классификация пропускается, но значение query не проверяется и не передаётся SDK: выбирается первая модель с `Complexity.MEDIUM`. Пустой список/неизвестная сложность/отсутствие совпадения дают `IndexError`, автоматического fallback нет. Контекстное окно, описание, цена и `settings.text_ai_model` при таком выборе не учитываются; порядок зависит от `created_at DESC`, явного tie-break нет. Это не описанный в неиспользуемых [prompts выбора модели](../src/llm_router/application/prompts.py) механизм и не гарантированная маршрутизация к запрошенному имени.

[`LLMImageRouter.call_llm`](../src/llm_router/application/llm_router.py) не читает registry и всегда использует `settings.image_ai_model` (`gpt-image-2` по умолчанию), независимо от query `model`. Обе ветки отправляются в `proxy_api_client`; общий текстовый клиент конструируется DI, но в этих двух ветках не вызывается.

Для text используется Redis key `ai_models`: TTL реализации **3600 с**, lock `lock:ai_models` на 10 с, ожидание до 50 × 0,1 с, затем самостоятельное чтение. При создании/удалении модели явной инвалидации нет; результаты до истечения TTL могут устареть. Ключ не содержит пагинацию (сейчас роутер всегда запрашивает одну страницу); только первые 50 записей участвуют в выборе. Протокол в [`application/repos.py`](../src/llm_router/application/repos.py) указывает другой default TTL (300), но фактически используется default функции. [Redis-клиент](../src/core/redis/__init__.py) создан с `decode_responses=True`, поэтому `get(lock_key)` возвращает строку. Но [освобождение lock](../src/llm_router/infra/cache.py) сделано неатомарно (`get` → `delete`): если TTL истечёт между этими операциями, возможна гонка с новым владельцем. Этот lock не следует считать гарантированным межпроцессным mutex.

## Вызов, парсинг и повторы

[`_invoke_once`](../src/llm_router/application/llm_router.py) вызывает OpenAI-compatible Responses API с `model_dump(exclude_none=True, by_alias=True)`. [`parse_llm_response`](../src/llm_router/infra/parse_response.py) сохраняет все output items (включая `reasoning`, `message`, `function_call`) в истории; собирает `output_text`, разбирает аргументы tools и `usage.total_tokens` (0 при отсутствии usage). `response.error` приводит к `ValueError`, любой `status=incomplete` — к `StructuredOutputError`. Для `text.format.type=json_schema` без tool calls требуется непустой JSON-**объект**: внешний markdown fence допускается, `json_repair` используется только если текст начинается с `{`; массив, пустой/произвольный текст отклоняются. При наличии tools `output` остаётся `None`; предметная Pydantic-валидация final tool выполняется позже в [`LLMTextService`](../src/llm_service/services.py), за пределами retry роутера.

[`LLM_RETRY`](../src/llm_router/application/llm_router.py) основан на [tenacity strategy](../src/llm_router/infra/strategy.py), `reraise=True`. Для OpenAI `APIStatusError` повторяются только 429, 500, 502, 503, 504 — до **4 попыток всего**; остальные OpenAI HTTP-статусы (например 400/401/403/404) не повторяются. `StructuredOutputError` и прочие `Exception` (в том числе транспортные и ошибки парсинга/нашего кода) — до **3 попыток всего**. Задержка после 429: числовой `retry-after` либо 5/10/20 с (cap 60); для 5xx — 3/6/12 с (cap 30); прочие — 1/2 с (cap 5). Это не 3/4 _дополнительных_ ретрая. Text `disable_retries=True` отключает tenacity на `_invoke`, но не SDK/внешние механизмы; image-путь этого флага не имеет. Классификатор вызывается отдельно с теми же правилами tenacity, но его ошибки `aiohttp` не являются `openai.APIStatusError` и попадают в общий класс повторов. Другие OpenAI `APIStatusError` с 5xx, например 501, не повторяются; для не-OpenAI исключений HTTP-статус не распознаётся, и применяется общая ветка с тремя попытками.

Оба [OpenAI-клиента](../src/core/providers/__init__.py) имеют `max_retries=0`, `timeout=340` (SDK); [классификатор](../src/llm_router/application/llm_router.py) создаёт отдельную `aiohttp.ClientSession` на запрос с настройками timeout по умолчанию, без явного общего дедлайна. В [общем внутреннем HTTP-клиенте](../src/shared/infra/services/client.py) `ClientTimeout(total=config.timeout)` — **секунды** (default 300), хотя описание поля в [config](../src/shared/infra/services/config.py) говорит «миллисекунды». Это отдельный таймаут HTTP-вызова потребителя, не общий дедлайн классификации + нескольких SDK-вызовов + ожиданий retry + загрузки файла. [Внутренний `LLMTextService`](../src/llm_service/services.py) задаёт `disable_retries=True` на каждый свой model step, ограничивая loop `max_model_requests=3`; его `_send_request` не проверяет HTTP status до валидации JSON как DTO.

Image `track_image_invocation` оборачивает retry-блок: tenacity повторяет только внутреннюю генерацию/вызов провайдера, а сохранение результата в media выполняется **снаружи** retry. Сбой media сам по себе не повторяет генерацию внутри этого вызова роутера; повтор всего HTTP-запроса вызывающей стороной может сделать новый платный вызов. Наружный декоратор публикует один итоговый event, а не event на каждую внутреннюю попытку. Text `track_text_invocation` оборачивает `_invoke_once`: событие публикуется **на каждую попытку** SDK/парсинга, классификация в эти события не входит. Нет общего ограничения числа вызовов провайдера при повторах от вызывающей стороны.

## Учёт, хранение и media

[`track_invocation.py`](../src/llm_router/application/track_invocation.py) замеряет `perf_counter`, берёт request ID из [request context](../src/shared/infra/request_context.py) или создаёт UUID, отправляет [`LLMInvocationCreated`](../src/llm_router/domain/events.py) со статусом `completed`/`failed`, токенами и сериализованными request/response. Сбой основного вызова повторно выбрасывается. [`_publish_invocation`](../src/llm_router/application/llm_router.py) логирует и **подавляет обычные исключения** от публикации; успех HTTP не означает, что учёт записан. На успехе image сначала сохраняет base64 результата в `llm-outputs` и подменяет поле `image` на ключ; на ошибке загрузки событие фиксирует failure и известные токены, но ответ клиенту не возвращается. `duration_ms` успешного image замеряется **до** загрузки в media, на failure — после ошибки.

[DI event publisher](../src/shared/dependencies/events.py) использует [RabbitMQEventPublisher](../src/shared/infra/events/rabbitmq.py), exchange приложения и routing key `llm_router.invocation.created`. [Очередь](../src/llm_router/infra/invocation_rabbit.py) `llm_invocation_created` durable; consumer ограничен семафором до 5 одновременных записей. Он заменяет входные base64-изображения ключами media в `llm-inputs`, затем создаёт запись `llm_invocations` с `id=event.event_id` и делает commit. Публикация и SQL commit не атомарны; для повторной доставки один event ID может конфликтовать по первичному ключу. Гарантий exactly-once или компенсации частично загруженных файлов этот код не даёт.

[`MediaClient`](../src/llm_router/infra/external_apis.py) принимает PNG/JPEG/GIF/WebP, проверяет base64 и максимум 20 MiB, создаёт presigned upload через `/api/v1/attachments/presigned-upload`, загружает байты на выданный URL **отдельной сессией без OAuth заголовка** (`total=120`, `connect=10`, `sock_read=60` с) и подтверждает `/api/v1/attachments/confirm-upload/{id}`. Внутренний HTTP-клиент получает M2M OAuth токен через [`SrvBaseClient`](../src/shared/infra/services/client.py) и конфиг `SRV_LLM_ROUTER_*` в [`infra/services/config.py`](../src/llm_router/infra/services/config.py). Путь загрузки зависит от media API, доступности storage/S3 и прав service account. Вызовы к media происходят также в consumer, уже после публикации события.

## Доступ, ошибки и операционные ограничения

[Identity](../src/iam/dependencies/identity.py) проверяет Bearer JWT, claims и blacklist, но не перечитывает членство/права из БД. [Permissions](../src/llm_router/domain/permissions/ai_models.py) `ai_model:create` и `ai_model:delete` — GLOBAL, проверяются [dependency](../src/iam/dependencies/permissions.py); поиск и ответы требуют лишь identity. Нет отдельной квоты, permission или resource ACL на `/responses/*`: аутентифицированный вызывающий может инициировать внешние платные вызовы. Название модели в query не служит ACL. Учёт сохраняет полные JSON request/response, в том числе содержимое сообщений и до обработки consumer — base64 входных изображений; [лог публикации](../src/llm_router/application/llm_router.py) также включает request/response/error. Это чувствительные данные: отдельно оценивать ретенцию, доступ к логам/очереди/БД и стоимость провайдеров.

[Обработчики приложения](../src/shared/api/exception_handler.py) возвращают `DomainError` как `{ "error": { "code", "message", "details" } }` с его status (например 401 отсутствие Bearer, 403 недостаточно permission, 400 `BadRequestError` валидации изображения). `ValueError`, включая `StructuredOutputError`, → 400 с `{ "error": { "grant": "VALIDATION_ERROR", "message", "status": 400, "details": {} } }`. Невалидный body/path → FastAPI 422 (`detail`). Необработанные ошибки SDK, SQL, media `SrvBaseError`, `IndexError` выбора модели не имеют здесь специального HTTP-маппинга и обычно доходят как 500; HTTP-статус провайдера не проксируется автоматически. Удаление несуществующей записи возвращает 204, не обещанный в старом README 404. Никаких сетевых ответов провайдера/отмены удалённой операции эти обработчики не гарантируют.

Конфигурация: [`core/providers/config.py`](../src/core/providers/config.py) читает `AITUNNEL_KEY`, `AITUNNEL_BASE_URL`, `PROXY_API_KEY`, `PROXY_API_BASE_URL` (placeholder-значения не являются рабочими ключами); [`core/settings.py`](../src/core/settings.py) — `IMAGE_AI_MODEL`, `TEXT_AI_MODEL`, `BASE_LLM_ROUTER_URL`. Последние два поля сейчас не участвуют в выборе text-модели или настройке сервисного клиента соответственно. URL классификатора захардкожен и может не совпасть с `AITUNNEL_BASE_URL`. Нужны PostgreSQL, Redis, RabbitMQ, два провайдера, media API и storage; `langsmith` traceable оборачивает вызовы (конфигурация трассировки в settings). Не запускать внешний smoke-check без тестовой конфигурации: он создаёт платные обращения и может записать чувствительные данные.

## Тесты, расхождения и открытые вопросы

Существуют [регрессионные xfail-тесты](../tests/unit/llm_router/test_router_regressions.py) выбора и загрузки, [тесты API-моделей e2e](../tests/e2e/test_llm_router_models_api.py), [тесты HTTP-ответов](../tests/integration/test_llm_router_api.py), а также [тесты учёта](../tests/unit/llm_router/test_invocation_monitoring.py), [consumer](../tests/unit/llm_router/test_invocation_rabbit.py) и [media](../tests/unit/llm_router/test_media_client.py). Часть тестов импортирует уже отсутствующие `src.llm_router.services`, `domain.vo`, `infra.media_client` или старый метод `invoke`; их ожидания не являются контрактом текущего кода. В частности, xfail про `final_tool_name` уже не соответствует сигнатуре [парсера](../src/llm_router/infra/parse_response.py), а xfail о retry после сбоя media противоречит текущему порядку декораторов: сохранение находится вне retry. В этой документационной задаче тесты поведения не запускались.

Остаётся уточнить продуктовый контракт query `model` (строго запрошенная модель, выбор по сложности или запрещённый параметр), правила fallback при пустой/устаревшей registry и допустимость расходов/хранения payload для любого authenticated identity. Без запуска в изолированной среде не подтверждены фактические ответы сторонних провайдеров, успешность OAuth/media upload, соблюдение взаимного исключения Redis lock при гонке и гарантии доставки RabbitMQ. Из удалённого README перенесены назначение, границы модуля, перечень endpoint и вопросы прав/ошибок, но фактические пути, DTO, статусы и учёт уточнены по исходникам.
