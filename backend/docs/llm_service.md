# `llm_service`: клиентский model/tool loop

`llm_service` — асинхронная клиентская оркестрация текстовых и графических вызовов LLM. Она формирует HTTP-запросы к `llm_router`, обрабатывает ответы и исполняет инструменты, но не предоставляет собственного HTTP API, не выбирает провайдера и не хранит историю самостоятельно. Это обновлённое описание вместо прежнего README модуля; отдельный исходный документ удалён после переноса актуальных сведений. Основные точки входа: [экспорты](../src/llm_service/__init__.py), [сервисы](../src/llm_service/services.py), [DTO](../src/llm_service/schemas.py), [инструменты](../src/llm_service/tools.py) и [middleware](../src/llm_service/middleware.py).

## Граница и зависимости

```text
потребитель (courses) → LLMTextService / LLMImageService
                    → SrvBaseClient (OAuth client_credentials, aiohttp)
                    → POST /api/v1/responses/text|image (CurrentIdentity)
                    → llm_router → OpenAI-compatible SDK / image provider
```

Сервис получает `client: SrvBaseClient`; `_send_request()` берёт авторизованную сессию через `_get_token_session()`, отправляет `request.model_dump(exclude_none=True)` и валидирует JSON ответа через `response_model.model_validate(...)`. Он **не** вызывает `raise_for_status()` и не переводит ошибки HTTP в специальное исключение: тело ошибки может дать `ValidationError`, сбой JSON или исключение aiohttp. Сессия и токен принадлежат клиенту: контекст `_get_token_session()` не закрывает общий `ClientSession` после запроса; закрывать клиент надо в его владельце. У клиента настроены общий HTTP timeout, пул, обновление токена под lock и `close()` ([реализация](../src/shared/infra/services/client.py), [конфигурация](../src/shared/infra/services/config.py)). В курсах используется [course_client](../src/courses/infra/services/client.py).

Маршруты [роутера](../src/llm_router/api/v1/llm.py) требуют `CurrentIdentity`; `llm_service` сам не проверяет полномочия на курс, чат или вызов инструмента. `model` из конструктора добавляется к URL как `?model=...`, без URL-кодирования в этом коде. При `model=None` text-router классифицирует задачу и выбирает модель из реестра; **при заданном `model` текущая реализация выбирает первую модель сложности `MEDIUM`, а не переданное имя** ([`LLMTextRouter.call_llm`](../src/llm_router/application/llm_router.py)). Image-router игнорирует аргумент `model` и использует `settings.image_ai_model`. Не следует считать query-параметр гарантией выбора конкретной модели.

## Контракты вызова и ответа

| Вызов                                           | Вход                                                                                                                                                                                                                                             | Выход                                                                                                                                |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| `LLMTextService.invoke(messages, schema=None)`  | История `messages`; опциональный класс `BaseModel` для финального результата. Конструктор принимает `system_prompt`, `tools`, `middlewares`, `runtime`, `reasoning`, `temperature`, `model`; defaults: `max_parallel=4`, `max_model_requests=3`. | `LLMTextResponse`: `output` (словарь или `None`), `raw_text` (словарь, строка или `None`), `tool_calls`, `messages`, `total_tokens`. |
| `LLMImageService.invoke(messages, images=None)` | Строка prompt; `images` — 1–5 base64-изображений, если переданы.                                                                                                                                                                                 | `LLMImageResponse`: `image` — ключ сохранённого изображения, а не base64; также `size`, `total_tokens`, `output_format`.             |

При вызове через [этот сервис](../src/llm_service/services.py) оба DTO сериализуются как `model_dump(exclude_none=True)` **без `by_alias=True`**: фактический HTTP-ключ в обоих запросах — `messages`, `None`-поля отбрасываются. DTO определяют алиасы `input` (текст) и `prompt` (изображение); роутер принимает и алиасы, и имена полей благодаря `populate_by_name=True` ([схемы](../src/llm_service/schemas.py)). При передаче DTO с `by_alias=True` клиент отправил бы `input`/`prompt`, но это не wire format данного сервиса. Провайдер возвращает image в base64, после чего [роутер сохраняет его через media](../src/llm_router/application/track_invocation.py) и возвращает ключ; ошибка сохранения не даёт успешного ответа. `LLMImageRequest` по умолчанию задаёт `quality=medium`, `size=1024x1024`, `output_format=png`; сервис эти параметры в `invoke()` не выставляет. Router вызывает `images.generate` без входных изображений и `images.edit` с ними ([image router](../src/llm_router/application/llm_router.py)). `Runtime[Context, State]` хранит `context`, необязательное `state` и `messages`; перед каждым вызовом модели сервис заменяет `runtime.messages` копией текущего input (или строкой для image). Это данные для middleware/tools, не persistent checkpoint. DTO и псевдопротоколы находятся в [schemas.py](../src/llm_service/schemas.py) и [protocols.py](../src/llm_service/protocols.py); в протоколах ещё упоминаются `base_url`, `timeout`, `_process_response`, которых текущие сервисы не предоставляют — опираться на них как на работающий API нельзя.

## Текстовый model/tool loop

В [`LLMTextService.invoke`](../src/llm_service/services.py) сначала строится список строгих function tools из `tools.values()`. `system_prompt` идёт как `instructions`. Конструктор сразу проверяет диапазон `temperature` и положительность `max_parallel`/`max_model_requests` (`ValueError` при нарушении).

Каждая итерация, не более `max_model_requests`, делает **один** POST `/api/v1/responses/text`: в теле `messages` — текущая история (алиас DTO — `input`), `tools`, `instructions`, `reasoning`, `temperature`, `disable_retries=True`, `final_tool_name` (если есть схема). Роутер не отправляет два последних поля провайдеру; `disable_retries=True` отключает tenacity-повторы **текстового вызова роутера**, но не создаёт общий deadline и не предотвращает повтор из внешнего слоя. На каждом ответе сервис разделяет `tool_calls` на обычные и финальные:

1. Без `schema` и без вызовов tools возвращает ответ сразу (включая `raw_text` и историю).
2. Обычные tools исполняет через цепочку `wrap_tool_call` и `asyncio.gather`; результаты `function_call_output` присоединяет к `response.messages` и делает следующий модельный вызов.
3. При `schema` успешным завершением считается **ровно один** отдельный `submit_final_result` с валидными аргументами. Он не исполняется как Python-функция: его аргументы проверяются Pydantic, записываются в `response.output` как исходный dict; к `messages` добавляется `function_call_output` «Final result accepted.», `tool_calls` очищается. Отдельный текстовый ответ при `schema` не завершает задачу: в историю добавляется пользовательское напоминание о финальном tool.
4. Несколько финальных вызовов или финальный вместе с обычными получают tool feedback с ошибкой; обычные tools при смешанном ответе всё равно исполняются. Ошибочные аргументы финального вызова получают feedback и возможность исправиться в следующей итерации.
5. Если бюджет исчерпан, выбрасывается [`ModelRequestLimitError`](../src/llm_service/exceptions.py) (`ValueError`), а не возвращается частичный результат. Число запросов ограничено **для одного `invoke`**, не для вложенных агентов и не для роутера/провайдера в целом.

`total_tokens` в возвращаемом DTO берётся из **последнего** модельного ответа, а не суммируется по loop. Даже `max_model_requests=1` может выполнить tools, а затем закончиться ошибкой бюджета, не дойдя до следующего запроса. Посторонние эффекты уже исполненных tools при ошибке/повторном запуске не откатываются.

## Tools: схема, аргументы, выполнение

[`@tool(name=..., description=...)`](../src/llm_service/tools.py) превращает **асинхронную** функцию в [`StructuredTool`](../src/llm_service/dataclasses.py). Имя и описание по умолчанию берутся из имени функции/docstring. Сигнатура превращается в Pydantic-модель аргументов с `extra="forbid"`; `self`, `cls`, `*args`, `**kwargs`, аргумент `runtime` и аргументы с маркером `Annotated[..., InjectedToolArg()]` не попадают в схему. Поля аргумента типа `BaseModel` расплющиваются на верхний уровень, затем модель собирается обратно при вызове. Конфликт имён полей вызывает `ValueError`. `InjectedToolArg` исключает аргумент из схемы, но только `runtime` автоматически подставляется при исполнении — для иных injected-аргументов нужен отдельный механизм.

[`to_strict_json_schema`](../src/llm_service/strict_schema.py) добавляет `additionalProperties: false` для объектов, перечисляет все свойства в `required`, рекурсивно обходит вложенные схемы/массивы/union, удаляет `default: null`, разворачивает `$ref` с соседними ключами. Строгая схема для провайдера не заменяет локальную Pydantic-валидацию. Ключи `tools` должны совпадать с именами `StructuredTool`: запрос формируется из **значений**, а поиск для исполнения выполняется по **ключу** словаря.

`run_tool()` валидирует аргументы, восстанавливает параметры и делает `await func(**kwargs)`; синхронные функции не поддерживаются этим вызовом. Результат превращается в `{"type":"function_call_output","call_id":...,"output":...}`; нестроковые результаты JSON-сериализуются с `ensure_ascii=False`. Для неизвестного имени сервис возвращает модели структурированный `{"error": ...}`. Для известного tool исключения наследников `Exception` (включая ошибку аргументов/JSON-сериализации) логируются и превращаются в общий `{"error": "Tool '...' failed ..."}`; исходная ошибка не передаётся модели и не пробрасывается вызывающему коду. Middleware может вернуть собственный output или выбросить исключение: его обёртка находится **снаружи** `_process_tool`.

Параллельные вызовы одного ответа запускаются `gather`, порядок feedback соответствует порядку вызовов, `Semaphore(max_parallel)` ограничивает **исполнение известных tools на экземпляре сервиса**, не глобальную конкуренцию, не middleware до семафора и не количество HTTP-запросов. `gather` не обеспечивает автоматическую отмену уже запущенных siblings при первом исключении middleware; возможны частичные эффекты. Не делите одну `AsyncSession` между конкурентными tools и не предполагайте идемпотентность записи при повторе. Отмена `asyncio.CancelledError` не подавляется `except Exception` в `_process_tool`, но может прервать ожидание HTTP/локальной задачи, не доказав остановку удалённого вызова или уже завершённых tools.

## Structured output и история Responses API

При `schema` сервис **не** использует `LLMTextRequest.format_schema()`/поле `text`: он добавляет специальный strict function tool `submit_final_result` и инструкцию вызвать его отдельно после остальных tools. Имя зарезервировано для этого сценария: пользовательскому tool с таким именем здесь не место. Router парсит аргументы финального вызова как JSON-object (запрещает нестандартные JSON-константы); ошибки кладёт в `ToolCallParsed.arguments_error`. Сервис дополнительно делает `schema.model_validate(deepcopy(arguments))`, возвращает модели список ошибок без значений input и при успехе оставляет в `output` исходный dict, **не** результат нормализации Pydantic. Поэтому потребители при необходимости валидируют ещё раз: [theorist](../src/courses/ai/agents/theorist.py), [researcher](../src/courses/ai/agents/reasoner.py), [course generator](../src/courses/ai/generation/course.py).

Поле `LLMTextRequest.format_schema()` доступно в DTO для прямых запросов с `text.format=json_schema`, но `LLMTextService.invoke(schema=...)` его не вызывает. В [парсере роутера](../src/llm_router/infra/parse_response.py) для такого прямого режима непустой JSON-object извлекается/восстанавливается и записывается в `output` только если нет tool calls; предметная Pydantic-валидация остаётся за потребителем. Пустой structured-ответ без tools, не-object JSON и любой ответ со статусом `incomplete` отклоняются `StructuredOutputError`. Для обычного text вызова `raw_text` — соединённые `output_text` (или fallback `response.output_text`), а `output` обычно `None`; не сводите все ответы к `output`.

`parse_llm_response()` добавляет к входной истории **каждый** output item Responses API (в том числе `reasoning`, `message`, `function_call`) без сведения в простой текст. В следующую итерацию передаются эта история и соответствующие `function_call_output` с теми же `call_id`; у финального вызова output добавляется перед возвратом. Если историю перезаписывать, нельзя разрывать `reasoning` и связанные с ним элементы или оставлять `function_call` без результата. Сам `llm_service` не сохраняет историю между вызовами: пример внешнего хранения — [`ChatCheckpointerMiddleware`](../src/courses/ai/middlewares/chat_checkpointer.py), который читает её до loop и записывает после полного завершения; [`SummarizationMiddleware`](../src/courses/ai/middlewares/summarization.py) сохраняет последние ходы и проверяет отсутствие незакрытых tool calls в отрезаемой части. При ошибке/отмене `after_agent` не выполняется, поэтому этот checkpointer не сохраняет незавершённый loop.

## Middleware и порядок хуков

Базовый [`BaseAgentMiddleware`](../src/llm_service/middleware.py) предоставляет pass-through хуки; сервис принимает последовательность в заданном порядке. `before_agent` вызываются перед всем `invoke` слева направо, `after_agent` — после успешного завершения **тоже слева направо**. `before_model` и `after_model` аналогично вызываются на **каждую итерацию запроса модели**, но не на каждую внутреннюю retry-попытку роутера. При исключении в хуке/вызове «after» не гарантирован: это не `finally`. `wrap_tool_call` строится в обратном порядке, так что первая middleware — внешняя обёртка каждого tool; она может изменить ответ, пропустить вызов или завершиться ошибкой.

Примеры из курсов: [InterviewerAgent](../src/courses/ai/external_agents/interviewer.py) располагает загрузку истории перед суммаризацией, затем ограничение вызовов и остановку интервью; [ToolCallLimitMiddleware](../src/courses/ai/middlewares/tool_limit.py) уменьшает счётчик только при результате без `error`, состояние хранится в экземпляре middleware; [ToolOutputCompressionMiddleware](../src/courses/ai/middlewares/compress_tools.py) сжимает большие outputs вне event loop; [StopInterview](../src/courses/ai/middlewares/stop_interview.py) изменяет `tool_calls` и `raw_text` после model. Такие изменения могут влиять на ветвление loop; у `StopInterview` удаление `tool_calls` при `schema=None` завершает loop, хотя в `messages` могут оставаться исходные `function_call` без outputs. Middleware с состоянием и `Runtime` не следует переиспользовать между одновременно выполняющимися `invoke` без отдельной синхронизации.

## Ошибки, повтор и стоимость

- Ошибка построения схемы/аргументов tool — локальный `ValueError`/`TypeError`; некорректный финальный ответ обычно превращается в feedback, затем при исчерпании бюджета — `ModelRequestLimitError`. Для обычного tool ошибка валидации аргументов при исполнении превращается в output с `error`, но некорректный JSON парсер [заменяет на `{}`](../src/llm_router/infra/parse_response.py), а [сервис](../src/llm_service/services.py) не проверяет `arguments_error` перед запуском: tool без обязательных аргументов может выполниться, несмотря на испорченный JSON. Не считать это защитой от побочных эффектов.
- `response.error` у роутера даёт `ValueError`; `incomplete` или неверный прямой JSON-schema output — `StructuredOutputError` ([парсер](../src/llm_router/infra/parse_response.py), [исключение роутера](../src/llm_router/domain/exceptions.py)). Вызов сервиса с `schema` не использует прямой JSON-schema режим. Локальная ошибка потребительской Pydantic-валидации не попадает в retry роутера.
- Текстовый сервис всегда устанавливает `disable_retries=True` для модельного запроса. При прямом вызове API без этого поля роутер применяет [tenacity-политику](../src/llm_router/infra/strategy.py): 429/5xx — до 4 попыток, прочие `Exception` (кроме некоторых OpenAI HTTP-статусов) — до 3; SDK и HTTP-клиент имеют собственные настройки. Image-router обёрнут в tenacity отдельно. Общий timeout HTTP клиента может закончиться раньше этих серий; `max_model_requests` не ограничивает количество вложенных агентов или image retries.
- Аутентификация к внутреннему API зависит от OAuth client_credentials в `SrvBaseClient`, доступ endpoint — от `CurrentIdentity` в роутере. Сбой сети, истечение timeout, ошибки provider/JSON/DTO/хуков выходят к caller без собственного HTTP mapping `llm_service`. Повторить весь `invoke` после ошибки можно только с учётом оплаченных вызовов и необратимых эффектов tools.

Отдельного каталога тестов `llm_service` в текущем дереве нет. Ближайшие проверки: [router regressions](../tests/unit/llm_router/test_router_regressions.py) (несколько `xfail` фиксируют прежние дефекты и могут устареть), [router unit](../tests/unit/llm_router/test_llm_router.py), [API unit](../tests/unit/llm_router/api/test_api.py), [API integration](../tests/integration/test_llm_router_api.py), [course tester](../tests/unit/courses/test_tester.py) и [practicer](../tests/unit/courses/test_practicer.py). Часть unit-тестов роутера импортирует прежние пути `src.llm_router.services`/`schemas`/`dependencies`, а тесты курсов — прежние пути `src.courses.agents...`; их не следует считать проверкой текущего loop без исправления коллекции. Integration требует подготовленного окружения/фикстур; запускать весь lifespan или рабочие сервисы как smoke-test небезопасно.

При изменении loop полезны изолированные тесты с подменённым `_send_request`/клиентом: текст без tools; tool → feedback → следующий запрос; успешный/ошибочный/смешанный `submit_final_result`; бюджет, middleware-порядок и исключения; неизвестный tool и сбой инструмента; отмена и `gather` с конкурентными эффектами; сохранение `reasoning`/`call_id` в истории; image DTO и lifecycle клиента. Для API отдельно проверять DTO, авторизацию и ошибки. В этом документе поведение описано по коду, а не подтверждено новым прогоном тестов.
