# Permissions


Каждый permission состоит из:

- `resource` — доменный ресурс, к которому относится право;
- `action` — действие над ресурсом;
- `code` — итоговый код права, обычно формируется как `<resource>:<action>`;
- `title` — человекочитаемое название права;
- `scopes` — допустимые уровни применения права.

## Scopes

Scopes определены в `src/iam/domain/vo.py` в `PermissionScope`.

| Scope | Значение | За что отвечает |
| --- | --- | --- |
| `global` | Глобальный уровень | Даёт право на уровне всей платформы. Обычно используется для системных администраторов и операций, которые не должны ограничиваться одной организацией, курсом или владельцем. |
| `organization` | Уровень организации | Ограничивает действие рамками конкретной организации/компании. Подходит для администраторов или менеджеров организации, которые управляют данными внутри своей организации. |
| `own` | Только свои данные | Ограничивает действие объектами, принадлежащими текущему пользователю. Используется для сценариев, где пользователь может читать или менять только собственные данные или созданные им сущности. |
| `course` | Уровень курса | Ограничивает действие рамками конкретного курса. Используется для доступа к содержимому или управлению в пределах отдельного курса. |
| `object` | Уровень объекта | Предназначен для максимально точной объектной авторизации. В текущих системных permissions не используется, но может применяться для доступа к конкретному объекту при наличии object-level policies. |

Важно: наличие permission проверяется двумя способами:

- `require_permissions(...)` — FastAPI dependency, проверяет только наличие нужного кода permission у текущего identity;
- `authorize(identity, permission, resource=None)` — проверяет наличие permission, а если передан `resource`, дополнительно применяет зарегистрированные политики доступа к конкретному объекту.

## IAM: permissions

Модуль: `src.iam.domain.permissions.permissions`

Ресурс: `permissions`

### `permissions:read`

- Константа: `READ`
- Action: `read`
- Title: `Просмотр списка прав`
- Scopes: `global`

Отвечает за доступ к просмотру списка всех permissions, зарегистрированных в системе.

Это административное право: пользователь с ним может открыть справочник прав и увидеть, какие ресурсы, действия и scopes доступны для назначения ролям. Так как permission имеет только `global` scope, предполагается, что просмотр всей матрицы прав доступен только на уровне платформы, а не внутри отдельной организации.

Текущее применение:

- `GET /permissions` в `src/iam/api/v1/permissions.py`

Практический смысл:

- нужно для экранов администрирования ролей и прав;
- позволяет строить UI выбора permissions при создании или редактировании ролей;
- не даёт само по себе права изменять роли или назначать permissions, а только читать список доступных прав.

## IAM: users

Модуль: `src.iam.domain.permissions.users`

Ресурс: `users`

### `users:read`

- Константа: `READ`
- Action: `read`
- Title: `Просмотр пользователей`
- Scopes: `organization`, `own`

Отвечает за просмотр пользователей.

Возможные уровни применения:

- `organization` — пользователь может просматривать пользователей в рамках своей организации;
- `own` — пользователь может просматривать только собственную пользовательскую запись/профиль.

Практический смысл:

- просмотр списка участников организации;
- открытие карточки пользователя;
- просмотр собственного профиля;
- основа для пользовательских и административных разделов IAM.

Это право не должно использоваться для изменения данных пользователя — только для чтения.

### `users:update`

- Константа: `UPDATE`
- Action: `update`
- Title: `Изменение пользователей`
- Scopes: `organization`, `own`

Отвечает за изменение пользовательских данных.

Возможные уровни применения:

- `organization` — администратор или менеджер организации может изменять данные пользователей внутри своей организации;
- `own` — пользователь может изменять только собственные данные.

Практический смысл:

- редактирование профиля пользователя;
- изменение данных участника организации администратором;
- обновление пользовательских настроек или контактной информации, если такие операции реализованы.

Важно разделять сценарии:

- изменение своего профиля должно проверяться через `own`;
- изменение чужих пользователей должно требовать `organization` и дополнительной проверки принадлежности к организации.

### `users:deactivate`

- Константа: `DEACTIVATE`
- Action: `deactivate`
- Title: `Деактивация пользователя`
- Scopes: `organization`

Отвечает за деактивацию пользователя в рамках организации.

Scope только `organization`, потому что деактивация — административное действие. Пользователь не должен деактивировать произвольные аккаунты глобально и обычно не должен самостоятельно деактивировать себя через то же право, которое используется администраторами организации.

Практический смысл:

- отключение доступа сотрудника/участника организации;
- временная или постоянная блокировка пользователя внутри организационного контура;
- управление жизненным циклом аккаунтов в организации.

При реализации endpoint-ов для деактивации важно дополнительно проверять, что целевой пользователь относится к той же организации, где действует право.

## Organization

Модуль: `src.organization.domain.permissions.organizations`

Ресурс: `organization`

### `organization:create`

- Константа: `CREATE`
- Action: `create`
- Title: `Создание организации`
- Scopes: `global`

Отвечает за создание новых организаций на платформе.

Так как право доступно только в `global` scope, создание организаций считается платформенной административной операцией. Обычный пользователь или администратор отдельной организации не должен создавать новые организации без глобальных полномочий.

Практический смысл:

- создание компании/тенанта в системе;
- первичная настройка организационного пространства;
- onboarding новой организации администратором платформы.

### `organization:read`

- Константа: `READ`
- Action: `read`
- Title: `Просмотр списка организаций`
- Scopes: `global`, `own`

Отвечает за просмотр организаций.

Возможные уровни применения:

- `global` — просмотр всех организаций на платформе;
- `own` — просмотр только своей организации или организаций, к которым относится текущий пользователь.

Практический смысл:

- глобальный администратор видит список всех организаций;
- пользователь видит информацию о своей организации;
- используется для справочников, профиля организации и административных экранов.

### `organization:update`

- Константа: `UPDATE`
- Action: `update`
- Title: `Изменение организации`
- Scopes: `organization`, `own`, `global`

Отвечает за изменение данных организации.

Возможные уровни применения:

- `global` — изменение любой организации на платформе;
- `organization` — изменение организации в рамках организационного администрирования;
- `own` — изменение своей организации, если пользователь связан с ней как владелец или администратор.

Практический смысл:

- редактирование названия, описания и настроек организации;
- обновление реквизитов или профиля компании;
- управление организацией глобальным администратором или уполномоченным пользователем организации.

Для безопасной реализации нужно проверять не только наличие `organization:update`, но и то, что пользователь действительно имеет отношение к изменяемой организации, если scope не `global`.

### `organization:delete`

- Константа: `DELETE`
- Action: `delete`
- Title: `Удаление организации`
- Scopes: `global`

Отвечает за удаление организации.

Право доступно только глобально, потому что удаление организации — потенциально разрушительная операция, затрагивающая пользователей, курсы, роли, членства и другие связанные данные.

Практический смысл:

- удаление тестовой или ошибочно созданной организации;
- административное удаление организации с платформы;
- потенциально soft-delete или hard-delete в зависимости от реализации сервиса.

Рекомендуется использовать дополнительные бизнес-проверки перед удалением: наличие активных пользователей, курсов, платежей, интеграций или других зависимостей.

## Courses

Модуль: `src.courses.domain.permissions.courses`

Ресурс: `course`

### `course:create`

- Константа: `CREATE`
- Action: `create`
- Title: `Создание курса`
- Scopes: `organization`, `own`

Отвечает за создание курса.

Возможные уровни применения:

- `organization` — пользователь может создавать курсы в рамках своей организации;
- `own` — пользователь может создавать курсы от своего имени или в личном пространстве, если такой сценарий поддерживается.

Текущее применение:

- `src/courses/api/v1/documents.py`: `document_to_markdown` и `upload_document` используют `authorize(identity, CREATE)` для операций с документами, связанными с созданием/подготовкой курса.

Практический смысл:

- создание нового курса вручную;
- загрузка материалов для генерации курса;
- подготовка документов, которые затем используются для построения курса;
- создание курса внутри организации пользователем с соответствующими правами.

Важно: для фактического создания курса в конкретной организации желательно дополнительно проверять организационный контекст, если endpoint получает organization id или создаёт курс внутри организации.

### `course:read`

- Константа: `READ`
- Action: `read`
- Title: `Просмотр списка курсов`
- Scopes: все значения `PermissionScope`: `global`, `organization`, `own`, `course`, `object`

Отвечает за просмотр списка курсов и общей информации о курсах.

Это самое широкое по scopes право в модуле курсов. Оно может использоваться в разных сценариях:

- `global` — просмотр всех курсов на платформе;
- `organization` — просмотр курсов своей организации;
- `own` — просмотр курсов, созданных пользователем или назначенных ему как владельцу;
- `course` — просмотр конкретного курса, к которому у пользователя есть доступ;
- `object` — просмотр конкретного объекта курса при объектной политике доступа.

Практический смысл:

- каталог курсов;
- список курсов организации;
- список курсов автора;
- административный просмотр курсов;
- выбор курса для дальнейшего редактирования или прохождения.

Это право отвечает именно за чтение списка/карточек курсов, но не обязательно за прохождение уроков. Для прохождения курса есть отдельное право `course:course_read`.

### `course:course_read`

- Константа: `COURSE_READ`
- Action: `course_read`
- Title: `Прохождение курса`
- Scopes: `course`

Отвечает за доступ к содержимому курса в режиме прохождения.

Scope только `course`, потому что это право должно работать в контексте конкретного курса: пользователь либо записан на курс, либо получил доступ к нему через роль/назначение/политику.

Текущее применение:

- `GET /lesson/basic/info/{lesson_id}` в `src/courses/api/v1/lesson.py`
- `GET /lesson/theory/{lesson_id}` в `src/courses/api/v1/lesson.py`

Практический смысл:

- просмотр базовой информации урока;
- чтение теоретических материалов;
- прохождение курса как студентом/слушателем;
- доступ к образовательному контенту без права редактировать курс.

Это право важно отделять от `course:read`: пользователь может иметь право видеть курс в каталоге, но не иметь права открывать его уроки и проходить обучение.

### `course:update`

- Константа: `UPDATE`
- Action: `update`
- Title: `Изменение курса`
- Scopes: `organization`, `course`, `own`

Отвечает за редактирование курса и его структуры.

Возможные уровни применения:

- `organization` — изменение курсов внутри организации;
- `course` — изменение конкретного курса, к которому пользователь назначен как редактор/преподаватель/администратор;
- `own` — изменение курсов, созданных текущим пользователем.

Текущее применение:

- `PUT /course/edit` в `src/courses/api/v1/course.py`
- `PUT /lesson/edit/{lesson_id}` в `src/courses/api/v1/lesson.py`
- `PUT /lesson/update/{lesson_id}` в `src/courses/api/v1/lesson.py`
- `edit_module` в `src/courses/api/v1/module.py`

Практический смысл:

- изменение названия, описания и параметров курса;
- редактирование модулей;
- редактирование уроков;
- обновление теоретических материалов и контентных блоков;
- работа преподавателя, автора курса или администратора организации.

Для операций редактирования конкретного курса/урока/модуля желательно проверять объектную принадлежность: например, что урок относится к курсу, где пользователь имеет scope `course`, или что курс принадлежит организации пользователя.

### `course:delete`

- Константа: `DELETE`
- Action: `delete`
- Title: `Удаление курса`
- Scopes: `organization`, `course`, `own`

Отвечает за удаление курса.

Возможные уровни применения:

- `organization` — удаление курсов в рамках организации;
- `course` — удаление конкретного курса при наличии права на этот курс;
- `own` — удаление курсов, созданных текущим пользователем.

Практический смысл:

- удаление черновика курса;
- удаление курса автором;
- удаление курса администратором организации;
- soft-delete курса, если сервис реализует мягкое удаление.

Так как удаление курса может затронуть уроки, модули, прогресс студентов и связанные материалы, перед выполнением операции рекомендуется проверять бизнес-ограничения и связи.

## LLM Router: AI models

Модуль: `src.llm_router.domain.permissions.ai_models`

Ресурс: `ai_model`

### `ai_model:create`

- Константа: `CREATE`
- Action: `create`
- Title: `Создание ии модели`
- Scopes: `global`

Отвечает за создание или регистрацию AI/LLM-модели в системе.

Scope только `global`, потому что модели — это инфраструктурный ресурс платформы. Их создание влияет на доступные провайдеры генерации, стоимость, маршрутизацию запросов и потенциально на безопасность данных.

Практический смысл:

- добавление новой модели в роутер LLM;
- регистрация модели провайдера;
- настройка модели, которая будет доступна для генерации курсов или других AI-функций;
- управление платформенным каталогом моделей.

Это право не означает право использовать модель для генерации. Оно отвечает именно за административное создание/регистрацию модели.

### `ai_model:delete`

- Константа: `DELETE`
- Action: `delete`
- Title: `Удаление ии модели`
- Scopes: `global`

Отвечает за удаление AI/LLM-модели из системы.

Scope только `global`, потому что удаление модели может сломать маршрутизацию AI-запросов, генерацию курсов, сохранённые настройки и зависимости, которые используют эту модель.

Практический смысл:

- удаление устаревшей модели;
- отключение модели, которая больше не поддерживается провайдером;
- удаление ошибочно созданной модели;
- административное управление списком моделей платформы.

Перед удалением модели рекомендуется проверять, используется ли она в активных настройках, курсах, генераторах, workflow или пользовательских сценариях.

## Рекомендации по использованию

1. Для простых endpoint-ов, где достаточно проверить наличие права, используйте `require_permissions(PERMISSION.code)`.
2. Для действий над конкретным объектом используйте `authorize(identity, PERMISSION, resource)`, чтобы кроме permission можно было применить object-level policies.
3. Не полагайтесь только на scope в роли: для `organization`, `course`, `own` и `object` почти всегда нужна дополнительная проверка принадлежности объекта.
4. `global` permissions стоит выдавать только системным администраторам платформы.
5. Разделяйте права чтения каталога и доступа к содержимому: например, `course:read` не равно `course:course_read`.
