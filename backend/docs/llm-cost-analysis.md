# Расходы на LLM при генерации курса: анализ и план оптимизации

Дата: 09.10.2026. Проверенная версия: ветка `task/SGK-035`, commit `9cec639`.

Это анализ существующего кода и предложения, а не уже внедрённые оптимизации. Production-код не изменялся, реальные LLM-запросы не запускались. Все пути ниже указаны относительно корня репозитория.

## 1. Главное

1. Перед основным вызовом почти всегда оплачивается ещё один вызов — выбор модели. В исследованных агентах генерации модель явно не задана. Выбор повторяется и на следующих оборотах инструментального цикла.
2. Выборщику передаётся весь запрос: инструкции, сообщения, схемы инструментов и ответа. В image-запросах туда попадают и входные Base64. Для известных этапов это лишняя работа: модель можно назначить конфигурацией.
3. Есть конкретный дефект базы знаний: при индексации не сохраняется текст чанка, хотя поиск читает его из payload. Это надо исправить до оценки качества RAG и полезности дополнительных исследований.
4. Повторы не ограничены только временными ошибками сети. Ошибка разбора уже полученного ответа внутри router может повторно вызвать модель. Ошибка S3 после генерации картинки может привести к повторению шага генерации.
5. Общего бюджета оборотов агентного цикла нет. Отдельные лимиты инструментов не ограничивают всю цепочку, критика и попытки инструментов, завершившиеся ошибкой.
6. `total_tokens` недостаточно для денег: не видны входные, кешированные, выходные и reasoning-токены, фактическая модель и все попытки. Возвращаемый результат `LLMTextService` содержит usage последнего оборота, а не сумму цепочки.

Первый практический пакет: корректный учёт → исправление RAG и платных повторов → назначение моделей известным этапам → бюджеты инструментов и контекста. Jev и Batch — отдельные эксперименты после этого, не обязательные новые компоненты.

### Что известно, а чего нет

В доступной локальной PostgreSQL нет записей, пригодных для расчёта фактических расходов: запрос к `llm_invocations` с исключением `TEST-%` и `test-model` вернул 0 записей. В локальной `ai_models` также 0 записей. Это сведения о локальном окружении, не о production.

Экспорта реальных LangSmith-трейсов и тарифов аккаунтов нет. Поэтому средние входные/выходные токены, реальные выбранные модели, частота ретраев и стоимость курса **не установлены**. Ни сохранённые JSON-примеры, ни тестовые записи Grafana не используются как платёжная статистика. В документе отделены факты кода, статические измерения и условные расчёты.

## 2. Полный путь курса

| Этап | Где смотреть | Что происходит и где оплачивается LLM |
| --- | --- | --- |
| Создание заготовки курса | `backend/src/courses/api/v1/course.py`, `application/services/course.py` | Создаётся сущность и сохраняется в PostgreSQL. Само создание не вызывает LLM. |
| Интервью пользователя | `backend/src/courses/api/v1/agents.py`, `agents/external_agents/interviewer.py` | LLM получает системные инструкции, историю чата, новый запрос, инструменты чтения материалов и завершения интервью. Возможны несколько оборотов на одно сообщение. |
| Подготовка контекста интервью | `backend/src/courses/agents/middlewares.py` | История загружается из БД; при достижении порога 70 000 токенов запускается отдельная платная суммаризация. |
| Постановка генерации в очередь | `backend/src/courses/agents/tools.py`, `course_generator/workflow.py` | `complete_interview` отправляет Dramatiq-задачу. Это не LLM-вызов само по себе. |
| Исследование и рассуждение | `backend/src/courses/agents/course_generator/nodes.py`, `subagents/reasoner.py` | Основной reasoner может вызывать researcher и critic. Их ответы возвращаются reasoner, после чего обычно нужен следующий LLM-оборот. |
| План курса | `backend/src/courses/agents/course_generator/nodes.py` | Один структурированный LLM-ответ с описанием модулей. Затем сохранение курса. |
| План каждого модуля | `backend/src/courses/agents/course_generator/subagents/module_builder.py` | Отдельный структурированный LLM-вызов на модуль. Затем сохранение модуля. |
| План каждого урока | `backend/src/courses/agents/course_generator/subagents/lesson_builder.py` | Отдельный структурированный LLM-вызов на урок с планом блоков. |
| Каждый контент-блок | `backend/src/courses/agents/course_generator/subagents/theorist.py` | Отдельный вызов на текст, тест, код, Mermaid, формулу или картинку. Для text/quiz доступны дополнительные вызовы `knowledge_search` и следующие LLM-обороты. |
| Сохранение картинки | `backend/src/courses/agents/middlewares.py`, `infra/media_client.py` | После ответа image-модели выполняется загрузка через media. Это не новый LLM-вызов, но ошибка здесь может повторить незавершённый шаг. |
| Сохранение урока и индексация | `backend/src/courses/agents/course_generator/subagents/lesson_builder.py` | SQL commit, затем embeddings и Qdrant. Внешняя генеративная LLM напрямую здесь не вызывается. |
| Готовность и выдача | `backend/src/courses/agents/course_generator/nodes.py`, `api/v1/course.py`, `api/v1/lesson.py` | Курс переводится в DRAFT, клиент опрашивает статус и читает сохранённый материал. Чтение результата не требует LLM. |
| Редактирование после генерации | `backend/src/courses/agents/external_agents/editor.py` | Новая платная генерация выбранного блока; в контекст передаются блоки курса/чата и выбранный блок. Учитывать отдельно от первоначального создания. |

В этой цепочке нет обязательного отдельного финального LLM-валидатора всего курса. Pydantic/TypeAdapter-валидация локальная и сама по себе токенов не расходует. Критик является инструментом reasoner, его фактическую частоту без трейсов определить нельзя. Mentor/tester/practicer — последующее использование платформы; их расходы не следует смешивать с ценой создания курса.

### На уровень ниже

Каждый оборот агента: `LLMTextService._run_loop` → HTTP `/api/v1/responses/text` → `LLMTextRouter.call_llm` → при отсутствии явной модели `_choose_model` → основной `_invoke` → разбор ответа → исполнение инструментов → следующий оборот, если нужны инструменты.

Изображения: `LLMImageService` → `/api/v1/responses/image` → выбор через текстовую модель → `_invoke_image` или `_invoke_image_based` → image-провайдер → сохранение через media.

Существующий `cache_ai_models` кеширует **список доступных моделей**, а не результаты LLM и не решения выборщика.

## 3. Каталог платных вызовов

Обозначения: M — число модулей, L — число уроков, B — число блоков, T — число сообщений пользователя в интервью. Один «вызов агента» может включать несколько обращений к провайдеру из-за инструментов и повторов.

| Тип | Модель сейчас | Состав промпта | Частота при новом полном запуске | Средние input/output и стоимость |
| --- | --- | --- | --- | --- |
| Выбор модели | `settings.text_ai_model`, для очень большого запроса — модель по размеру контекста | `PROMPT_CHOOSE_MODEL` + каталог моделей + полный исходный запрос + схема выбора | Перед каждым обращением без явной модели, включая продолжения tool-loop | Не измерены; стоимость по usage выборщика |
| Fallback неизвестной модели | Аналогичный текстовый выборщик | `PROMPT_RETRY` + каталог + запрос + запрошенное имя модели | Если явно переданное имя отсутствует в каталоге | Не измерены; дополнительный вызов |
| Интервью | Динамический выбор | `INTERVIEWER_PROMPT`, история, текущий запрос, схемы четырёх инструментов | Не менее одного оборота на обрабатываемое сообщение; продолжения увеличивают число | Не измерены |
| Суммаризация | Динамический выбор | `PROMPT_SUMMARIZE_CHAT` + текущая история | При достижении порога middleware; не фиксированное число на курс | Не измерены; экономия должна превышать цену самой суммаризации |
| Reasoner | Динамический выбор | `REASONER_PROMPT`, пользовательская задача, история инструментов | Один начальный оборот + продолжения | Не измерены |
| Researcher | Динамический выбор | `RESEARCHER_PROMPT`, задача исследования, результаты RAG/web/browse | До двух успешных вызовов инструмента researcher в одном экземпляре reasoner; внутри несколько оборотов | Не измерены |
| Critic | Динамический выбор | `CRITIC_PROMPT` с задачей + `runtime.messages` reasoner | По решению reasoner; отдельного лимита нет | Не измерены |
| Структура курса | Динамический выбор | `COURSE_STRUCTURE_PROMPT`, few-shot, результат reasoner, JSON Schema | 1 | Не измерены |
| Структура модуля | Динамический выбор | `MODULE_STRUCTURE_PROMPT`, few-shot, аудитория, цели и описание модуля | M | Не измерены |
| Структура урока | Динамический выбор | `LESSON_STRUCTURE_PROMPT`, few-shot, цели, описание и требования к блокам, JSON Schema | L | Не измерены |
| Text/quiz | Динамический выбор | Инструкции типа блока, few-shot, контекст урока, задание, схема, возможный RAG | По одному начальному обороту на такой блок + продолжения | Не измерены |
| Code/Mermaid/math/chemical/musical | Динамический выбор | Инструкции типа, few-shot, контекст урока, задание, схема | По одному на такой блок, без tools в текущей конфигурации | Не измерены |
| Image generation/edit | Динамический выбор image-модели; выборщик текстовый | Задание; при edit — исходные картинки | По одному на image-блок + повторы | Не измерены; нужен отдельный image-тариф |
| Editor | Динамический выбор | Запрос правки, блоки, выбранный блок, инструкции типа | По запросам редактирования; не часть минимального первого прогона | Не измерены |

В `backend/src/llm_router/dependencies.py` текстовый клиент направлен в AITUNNEL, image-клиент — в ProxyAPI. SDK-retries отключены (`max_retries=0`), timeout — 340 секунд. В локальном `.env` задан `TEXT_AI_MODEL=gpt-5-nano`. В коде default — `gemini-2.5-flash-lite`. Это модель **выборщика**, а не доказательство, что весь курс генерируется nano: основной ответ создаёт выбранная модель. Для image есть default `image_ai_model`, но текущая ветка `call_llm` всё равно проходит `_resolve_model`; нельзя считать default фактической выбранной моделью.

Каталог, который получает выборщик, содержит name/description/context, но не отдельные числовые тарифы. Поэтому требование «выбери самую дешёвую» без достоверных актуальных цен не гарантирует минимальную стоимость.

### Оценка числа обращений по структуре

Без интервью, суммаризации, дополнительных оборотов reasoner, researcher, critic, RAG, ошибок и редактирования число основных обращений для нового курса:

`N = 2 + M + L + B`

Два первых — начальный reasoner и план курса. Когда перед каждым обращением выполняется ещё один выбор модели, получаем примерно `2 × N` обращений к провайдерам. Это не универсальный нижний предел для resume: сохранённые шаги могут пропускаться.

| Сохранённый пример, не платёжный отчёт | M | L | B | Основные обращения по формуле | С выбором перед каждым |
| --- | ---: | ---: | ---: | ---: | ---: |
| `backend/course.json` | 10 | 63 | 318 | 393 | 786 |
| `backend/course_result.json` | 6 | 35 | 165 | 208 | 416 |

В первом файле: 177 text, 60 quiz, 54 program_code, 21 mermaid, 6 math_formula. Во втором: 86 text, 35 quiz, 36 mermaid, 8 math_formula. Изображений в этих двух примерах нет; их цену эти примеры не показывают. Происхождение файлов не подтверждает соответствующие реальные количества платных вызовов: это только разбор сохранённой структуры.

## 4. Статические измерения промптов

Подсчёт выполнен без вызовов моделей: AST извлечён из исходников, строки токенизированы локально `tiktoken/o200k_base`. Это размер фиксированного текста, **не среднее API usage**. JSON-обвязка, инструменты, схемы, динамические поля, история, reasoning и служебные токены провайдера сюда не входят. Для других семейств моделей токенизатор может отличаться.

| Фиксированная инструкция | Токены текста |
| --- | ---: |
| `PROMPT_CHOOSE_MODEL` | 1 281 |
| `REASONER_PROMPT` | 961 |
| `RESEARCHER_PROMPT` | 610 |
| `CRITIC_PROMPT` | 362 |
| `COURSE_STRUCTURE_PROMPT` | 583 |
| `MODULE_STRUCTURE_PROMPT` | 660 |
| `LESSON_STRUCTURE_PROMPT` | 787 |

| Few-shot | Токены содержимого сообщений | Токены сериализованного JSON-примера |
| --- | ---: | ---: |
| Course structure | 1 556 | 1 650 |
| Module structure | 1 417 | 1 491 |

Для сценария M=5, L=25 фиксированные инструкции и содержимое few-shot только трёх планировщиков составляют:

`(583 + 1556) + 5 × (660 + 1417) + 25 × (787 + 1473) = 69 024 токена`.

Это не токены всего курса и не счёт провайдера. При автоматическом выборе тот же текст дополнительно представляется выборщику; точный размер этой копии зависит от сериализации. В сценарии 393 выборов одна только инструкция выборщика занимает `393 × 1281 = 503 433` токена фиксированного текста до каталога и копии пользовательского запроса. Вывод: сначала стоит убрать ненужные выборы, а не только сокращать few-shot на несколько строк.

## 5. Проблемы и конкретные изменения

### 5.1. Выбор модели на каждом обороте

Где: `backend/src/llm_router/services.py` (`_resolve_model`, `_choose_model`, `_fallback_model`); места создания `LLMTextService`/`LLMImageService` в `nodes.py`, `module_builder.py`, `lesson_builder.py`, `reasoner.py`, `theorist.py` и `interviewer.py`.

Что сделать:

- Для известных этапов передавать существующий аргумент `model`, значение брать из конфигурации, а не выполнять LLM-классификацию. Для блоков подходит уже имеющийся `THEORIST_CONFIG`.
- Начать оценку с nano для простого структурирования, коротких преобразований и суммаризации. Для содержательной теории, сложного кода и критика подобрать модель по парным тестам. Не назначать дорогую финальную проверку без доказанной необходимости.
- До запуска проверять доступность выбранных моделей и их capabilities. Иначе отсутствующее имя активирует текущий платный fallback и ожидаемая экономия не получится.
- Для действительно неизвестных задач оставить автоматический выбор, но сравнивать допустимые модели по тарифу и возможностям, а не только по текстовому описанию.

Эффект: убирается стоимость выборщика на покрытых этапах. Если исчезает половина HTTP-вызовов, это **не означает** уменьшение денег на 50%: выборщик может быть намного дешевле основного ответа.

### 5.2. Полный запрос и Base64 у выборщика

Где: `_choose_model`, `_fallback_model`, `_select_model_by_length` в `backend/src/llm_router/services.py`.

Если выбор остаётся, передавать краткие признаки: тип задачи, язык, размер входа, требование structured output/tools/vision, сложность, допустимая задержка и бюджет. Не передавать историю целиком, Base64, полную схему ответа и внутренние промежуточные данные. Размер контекста вычислять локально; Base64 не является осмысленным текстом для выбора image-модели.

Сейчас порог `BASE_MODEL_CONTEXT=400000` не резервирует место для ответа и не проверяет окно каждой доступной модели для меньших запросов. Нужно проверять `input + ожидаемый output + запас <= context` конкретного кандидата. Ошибки контекста предотвращать до платного запроса. Признаки задачи должны сохранять ограничения по предмету и качеству, иначе короткий выбор станет дешёвым, но неверным.

### 5.3. Повторяющиеся инструкции, схемы, история

Где: `backend/src/courses/agents/course_generator/subagents/prompts.py`, `few_shots.py`, `backend/src/courses/agents/prompts.py`, `backend/src/llm_service/strict_schema.py`, `schemas.py`, `backend/src/courses/agents/middlewares.py`, `external_agents/editor.py`.

Что сделать:

- Проверить дубли между system prompt, user template, few-shot и descriptions JSON Schema. Оставить один источник правила; не удалять требования к структуре, учебным целям и корректности.
- Сначала сравнить один компактный пример с текущими few-shot, а не удалять все примеры вслепую.
- Для editor передавать выбранный блок и необходимый контекст урока/соседей, а не все блоки по умолчанию. Полный материал оставлять для правок, действительно зависящих от него.
- Повторяющиеся стабильные инструкции, tools и схемы сохранять в стабильном порядке; динамическое задание — после стабильного префикса. Подтвердить кеш по `cached_tokens` реального провайдера.
- Для длинных чатов сохранять резюме требований и последние сообщения; суммаризацию запускать только когда её цена окупается будущими обращениями. Не добавлять отдельную суммаризацию перед каждым коротким запросом.

Prompt caching провайдера переиспользует точный общий префикс, но не готовый ответ. Это отличается от нашего Redis-кеша результата. Поддержка и скидка при работе через прокси требуют проверки. [OpenAI: prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching).

Дополнительный риск качества: `LemmatizationMiddleware.process_conversation` перемещает нормализованные user/assistant-сообщения после остальных сообщений и меняет исходный текст. Нельзя считать это безопасным «сжатием контекста»: проверить порядок tool-сообщений, числа, код и смысл требований; нормализацию разумнее ограничить поисковым запросом. Исправление согласовать отдельно, не переписывать все middleware ради экономии.

### 5.4. Инструментальные циклы и условный критик

Где: `backend/src/llm_service/services.py` (`_process_response`, `_process_tool`); `backend/src/courses/agents/middlewares.py` (`ToolCallLimitMiddleware`); `subagents/reasoner.py`, `theorist.py`, `course_generator/tools.py`, `utils/browser_automation.py`.

Пример расходов: модель попросила поиск → инструмент вернул страницу → модель ещё раз обрабатывает всю историю → попросила критика → критик вызывает LLM → исходная модель снова читает его ответ. Платен не только инструмент-критик, но и продолжения основного агента. Чтение SQL/DDGS само по себе не равно LLM-вызову, однако его результат увеличивает следующий input.

Что сделать:

- В существующем `LLMTextService` учитывать общий бюджет оборотов на запуск агента, включая ошибочные инструменты. На исчерпании завершать контролируемым результатом, а не посылать ещё один такой же запрос.
- В существующий `ToolCallLimitMiddleware` добавить согласованные лимиты критика и RAG для text/quiz. Сейчас critic не ограничен; для theorist лимит по умолчанию не подключён.
- Лимит researcher=2 относится к одному экземпляру reasoner; researcher получает новые лимиты web=4, browse=5, knowledge=5 на каждом своём запуске. Ошибочные вызовы не уменьшают текущий счётчик. Общего конечного бюджета из этого не получается.
- В tool-output задать токен-бюджет, удалять навигационный мусор и дубли страниц, сохранять источники и релевантные разделы. Предпочесть отбор фрагментов простому обрезанию первых символов.
- Вызывать критика по явной необходимости: сложная тема, противоречие, провал локальной проверки. Простые схемы валидировать локально. Не обещать, что вероятностная оценка сама гарантирует качество.
- Числа лимитов подобрать на наборе коротких/сложных курсов, а не объявлять универсальные значения без измерений.

Отдельный лишний оборот виден при завершении интервью: `complete_interview` устанавливает task_id во время исполнения инструмента, затем `_process_response` снова вызывает `_run_loop`. `StopInterview` проверяет task_id только в `after_model`, то есть после ещё одного ответа LLM. Проверять штатное условие завершения нужно до следующего обращения, сохраняя существующий формат ответа с task_id. Это убирает продолжение и связанный выбор модели, а не сам содержательный этап интервью.

### 5.5. Платные повторы при ошибках вне модели

Где: `backend/src/llm_router/services.py` (`_invoke`, image-методы); `utils.py` (`is_retryable_error`, `stop_strategy`, `parse_llm_response`); `backend/src/courses/agents/course_generator/workflow.py`, `helper.py`, `subagents/lesson_builder.py`; `SaveImageMiddleware` в `agents/middlewares.py`.

Сейчас `_invoke` объединяет сетевой запрос и parse под `@retry`. `is_retryable_error` разрешает обычные `Exception`, включая ошибки нашего кода, и `StructuredOutputError`. Для перечисленных статусов 429/500/502/503/504 предусмотрено до 4 попыток всего; для остальных retryable ошибок — до 3. На уровне Dramatiq отдельно есть `max_retries=6`, то есть первоначальное выполнение и до 6 повторов задачи. Это разные уровни, не доказательство семикратного повторения всего курса: `invoke_or_resume` использует checkpoints.

Правила изменения:

1. Повторять запрос провайдера только при согласованных временных ошибках транспорта/сервиса. Разбор, TypeAdapter и сохранение не включать в тот же retry-блок.
2. Сохранять идентификатор ответа, usage и доступный сырой ответ до локального разбора. Уже есть JSON repair/extraction: сначала использовать их, а не начинать новую генерацию.
3. `incomplete` из-за лимита выхода не лечить неизменённым повтором. Диагностировать причину; разрешённую корректирующую попытку выполнять с изменённым бюджетом/условиями и учитывать отдельно.
4. Если нужна реальная правка содержания, посылать конкретную ошибку и проблемный фрагмент, ограничить число исправлений. Это платная repair-генерация, не бесплатный парсинг.
5. При timeout после отправки неизвестно, обработал ли провайдер запрос. Не считать попытку бесплатной; проверять возможность получить ответ по id и поддержку идемпотентности у конкретного API.
6. После успешной image-генерации ошибка media/S3 должна повторять загрузку сохранённого результата, не создание новой картинки. Менять границу выполнения в вызывающем коде, не переписывать модуль media.
7. `generate_content_blocks` возвращает готовый lesson только после завершения всех задач TaskGroup. Если одна падает, готовые результаты остальных блоков ещё не стали состоянием завершённого узла. Проверить fault-тестом и переиспользовать результат по `course/module/lesson/block + версии задания` до повторного вызова. Не заменять весь checkpointer ради этой задачи.
8. После SQL commit сбой индексации должен повторять индексацию идемпотентно. Случайные UUID вектора при каждом повторе могут создавать дубли; это отдельная проблема индексации, а не повод перегенерировать текст.

### 5.6. База знаний не возвращает сохранённый текст

Где: `backend/src/courses/infra/database/repos/vector_repo.py` (`index_document`, `retrieve_documents`), `backend/src/courses/agents/course_generator/tools.py` (`save_knowledge`, `knowledge_search`).

Сейчас для каждого чанка вычисляются векторы, но `payload=metadata or {}` не добавляет текст чанка. `save_knowledge` передаёт только course_id/source/category/score. При поиске код делает `payload.get("text", "")` и передаёт пустые строки в reranker. То есть вектор найден, а содержимое материала не возвращается как ожидается.

Минимальное исправление: для каждой точки сохранять metadata и **текст именно этого чанка** в поле `text`. Поле не должно перезаписываться произвольной metadata. Затем переиндексировать ранее созданные точки с исходных материалов; изменения одной функции недостаточно для старых данных.

Проверка: проиндексировать материал с уникальным фактом → найти его по вопросу → проверить непустой исходный фрагмент, источник и изоляцию course_id. Вызовы embed/rerank/Qdrant в unit-тесте замокать. Снижение числа web-поисков — гипотеза для проверки, а не уже измеренный эффект.

`backend/src/core/retrieval/rest.py` и `config.py` используют отдельные embeddings/reranker endpoints; default-модели — `deepvk/USER-bge-m3` и `BAAI/bge-reranker-v2-m3`, адреса localhost:7997/7998. Это вычислительные расходы инфраструктуры, не автоматически тариф OpenAI за текст. Для индексации можно передавать несколько чанков одним уже поддержанным `embed(inputs=[...])`, сохранив порядок результатов.

### 5.7. Большие ответы, reasoning и всплески параллелизма

Где: `backend/src/llm_service/services.py`, `schemas.py`; `backend/src/llm_router/services.py`; TaskGroup в `nodes.py`, `module_builder.py`, `lesson_builder.py`.

В текущей текстовой request-схеме нет `max_output_tokens`. Добавить согласованный лимит через существующие service/request/config слои, различающий план, короткий блок и длинную теорию. Проверять достаточность для схемы и reasoning. Reasoning-токены оплачиваются как output; лимит Responses охватывает и reasoning, и видимый ответ. Слишком низкий предел может дать incomplete и увеличить расходы на исправления. Не прибавлять reasoning второй раз, если оно уже входит в output_tokens. [OpenAI: reasoning](https://developers.openai.com/api/docs/guides/reasoning).

Одновременные модули → уроки → блоки создаются вложенными TaskGroup. Semaphore=4 в `LLMTextService` ограничивает инструменты одного экземпляра, не все запросы провайдеру. Нужен согласованный лимит in-flight запросов на провайдера и бюджет ретраев. При нескольких worker процессах локальный semaphore не равен общему лимиту. Последовательная генерация сама по себе не увеличивает токены, а параллельность сама по себе их не уменьшает: здесь цель — меньше 429/неопределённых timeout и повторов, а не искусственно сделать всё последовательным.

## 6. Как считать деньги

Для каждого фактического ответа/попытки фиксировать provider, запрошенную и фактическую model, response_id, course_id, stage, block_id при наличии, номер попытки и причину повтора, input_tokens, cached_input_tokens, output_tokens, reasoning_tokens при наличии, время и тариф/валюту. Не логировать ключи, Base64 и полный пользовательский материал ради cost-метрик.

Проверять семантику usage провайдера: cached является частью input, reasoning обычно частью output. Неизвестные значения хранить как неизвестные, не как 0. Стоимость image учитывать по его тарифу и параметрам quality/size, при необходимости отдельно text/image usage.

`backend/src/llm_router/utils.py` сейчас сохраняет в итоговой схеме только total_tokens; `to_langsmith_llm_output` выставляет input/output в None. `backend/src/llm_service/services.py` возвращает последний ответ tool-loop. Надёжнее учитывать каждую попытку на границе провайдера, включая выбор модели и ответы, после которых упал парсинг, и группировать по course_id. Суммирование этих записей не должно повторно добавлять total родительского span.

Для текстового вызова с тарифами за миллион токенов:

`cost = ((input - cached) × P_input + cached × P_cached + output × P_output) / 1_000_000`.

Стоимость создания курса = интервью + суммаризации + выбор моделей + все основные и дополнительные обороты + repair/retry + изображения. Embeddings, reranker, Redis/SQL/S3 учитывать отдельной инфраструктурной строкой. Правки пользователя после выдачи — отдельная метрика, с возможностью включить их в стоимость жизненного цикла.

Среднее считать только после сбора данных: суммы input/output/cost и число попыток по типу/модели. Для бизнес-метрики расходы на неудачные курсы также входят в числитель: `все расходы генерации / число успешно готовых курсов`. Иначе неудачные дорогие прогоны исчезнут из отчёта.

### Условный пример, не цена нашего курса

Официальный прямой тариф GPT-5 nano: $0.05/M input, $0.005/M cached input, $0.40/M output. Это **не тариф нашего аккаунта AITUNNEL**. На момент проверки официальная страница также помечает nano как deprecated: пример использует текущую локальную настройку, а не предлагает бессрочно закрепить эту модель. Доступность и срок поддержки через прокси проверить перед внедрением; автоматически заменять её в этом анализе не нужно. [OpenAI: GPT-5 nano](https://developers.openai.com/api/docs/models/gpt-5-nano).

Пусть один выбор требует 5 000 входных и 100 оплачиваемых выходных токенов, без кеша. Тогда 1 000 выборов стоят `$0.25 + $0.04 = $0.29` по прямому тарифу. Устранение всех этих выборов убирает именно $0.29, а не некоторый заранее известный процент от всей генерации. AITUNNEL публикует диапазон 10–22 ₽/M input и 80–176 ₽/M output. Для такого же условного объёма это 58–127.60 ₽ за 1 000 выборов; для фактического счёта нужен применённый тариф конкретного маршрута/аккаунта. [AITUNNEL: GPT-5 nano](https://aitunnel.ru/models/gpt-5-nano).

### Jev — стоит ли подключать

Jev возвращает типизированные решения, probabilities/confidence и подходит как кандидат на классификацию/маршрутизацию, а не замену генератору учебного текста. Это не готовый роутер, который знает наши тарифы и качество моделей. [TypeSafe: introduction](https://docs.typesafe.ai/introduction).

Публичный тариф Jev — $0.042/M input, output бесплатный; вход текстовый, есть ограничения контекста. Документация рекомендует проверять качество неанглийских задач. Готовый публичный self-hosted-вариант не подтверждён просмотренной документацией; локальное развёртывание и его цену нельзя обещать. [TypeSafe: models](https://docs.typesafe.ai/models).

В условном примере выше 1 000 решений Jev с тем же входом стоят $0.21: экономия $0.08, около 28% **только стоимости выборщика**, при непроверенном качестве. Если у nano из 5 000 input токенов 3 000 реально кешируются, nano стоит $0.155 за 1 000 таких решений — меньше $0.21. Разные токенизаторы и тарифы прокси делают это только иллюстрацией. Бесплатное детерминированное назначение известного этапа предпочтительнее покупки другого выборщика.

## 7. Сравнение оптимизаций

Порядок — приоритет внедрения, а не обещание точного денежного выигрыша. Проценты общего курса без baseline неизвестны; эффекты нельзя просто сложить, они пересекаются.

| Приоритет / изменение | Ожидаемая экономия и как измерить | Влияние на качество | Сложность | Риск |
| --- | --- | --- | --- | --- |
| P0: usage всех попыток и тарифы | Прямой экономии нет; появляется проверяемый baseline | Не меняет ответ | Низкая–средняя | Двойной учёт spans, отсутствующий usage, несоответствие тарифов |
| P1: текст чанка в RAG | Цена устранённых дополнительных исследований; точный эффект неизвестен | Должно восстановить доступ к материалам | Низкая для кода, средняя для переиндексации | Старый индекс остаётся пустым, нарушение course isolation |
| P1: убрать retry локального parse/save | Стоимость предотвращённых повторных генераций | Не должно ухудшить при сохранении исходного ответа | Средняя | Timeout не доказывает, что запрос не оплачен |
| P1: фиксированные модели этапов | До 100% стоимости выборщика на покрытых этапах, не всего курса | Проверить достаточность выбранных моделей | Низкая–средняя | Неверная модель, скрытый платный fallback |
| P1: компактный вход выборщика там, где он нужен | Удалённые input-токены × тариф + изменение кеша | Сохранить признаки сложности и capabilities | Низкая | Потеря важного требования |
| P1: общий бюджет оборотов и условный критик | Цена оборотов за пределом полезного бюджета | Возможна недоработка сложных тем | Средняя | Слишком низкий лимит, незавершённые tools |
| P2: сократить дубли, few-shot и историю | Удалённые оплачиваемые input-токены; учитывать потерю/рост cache hits | Обязателен парный quality-test | Низкая–средняя | Ухудшение формата, фактов или обучения |
| P2: кеш префикса провайдера | `cached_tokens × (P_input - P_cached)` | Не меняет результат семантически | Низкая, если поддержан провайдером | Кеш не срабатывает или прокси не применяет скидку |
| P2: кеш готового результата и single-flight | Стоимость точных cache hits и предотвращённых одновременных дублей | Безопаснее для точных совпадений | Средняя | Чужие данные, устаревшие материалы, повтор tools с side effects |
| P2: лимиты output/reasoning | Сокращение оплачиваемого output минус цена дополнительных repair | Может обрезать содержание | Низкая–средняя | Incomplete и больше перегенераций |
| P2: лимит concurrency | Экономия только на предотвращённых ошибках/дублях, не нормальных вызовах | Обычно не меняет содержание | Средняя | Увеличение задержки, многопроцессный обход лимита |
| P3: Batch для независимых offline-этапов | OpenAI заявляет 50% скидку на поддерживаемые Batch-запросы; не весь курс | Те же задачи, но другой SLA | Средняя–высокая | До 24 часов ожидания; прокси может не поддерживать |
| P3: Jev для неизвестных задач | Разница полной стоимости решений и последствий маршрутизации | Проверить русский язык и сложные случаи | Средняя | Новый провайдер, confidence не гарантия качества |

Batch рассматривать для заранее подготовленных независимых заданий, например отдельных блоков после планирования или offline-evals. Не использовать его для интерактивного интервью и зависимого tool-loop. `asyncio.gather`/TaskGroup не предоставляют скидку Batch. [OpenAI: Batch API](https://developers.openai.com/api/docs/guides/batch). AITUNNEL публикует Batch-тарифы nano, но совместимость нужного endpoint и доступность в нашем аккаунте не проверены; для ProxyAPI это также требует отдельной проверки. [AITUNNEL: GPT-5 nano](https://aitunnel.ru/models/gpt-5-nano).

### Кеширование без нового «фреймворка»

Для точных результатов переиспользовать `Cache`/`RedisCache` из `backend/src/shared/infra/cache/base.py` и `redis.py`; не писать второй Redis-клиент. Ключ должен учитывать provider/model, параметры generation, версии промпта и схемы, вход, права/tenant и версию знаний курса. Кешировать только валидный завершённый результат, не ошибки и не неисполненные tool side effects.

Single-flight — отдельная защита от одновременных одинаковых запросов: один выполняет работу, остальные ждут его результат. Обычный get/set этого не гарантирует; нужен согласованный механизм блокировки с TTL, владением и обработкой падения. Сначала проверить частоту точных дублей; semantic cache с похожими запросами не внедрять первым из-за риска подмены учебных требований.

## 8. План изменений с минимальным вмешательством

1. **Учёт без изменения генерации.** На границе провайдера в `llm_router` собирать usage каждой попытки и stage/course correlation; держать версионированные тарифы в конфигурации. Не увеличивать бизнес-схемы и колонки автоматически: место хранения согласовать с текущим мониторингом/LangSmith.
2. **Исправления явных потерь.** Добавить chunk text в существующий VectorRepository, переиндексировать источники. Разделить provider-retry и parse/save, сохранить готовый ответ для повторной обработки. Проверить восстановление отдельного блока и загрузки картинки. Media и Redis-checkpointer не переписывать.
3. **Дешёвый маршрут известных этапов.** Передать `model` в существующие конструкторы агентов из конфигурации этапов/`THEORIST_CONFIG`. Проверить каталог до начала работы. Для оставшегося chooser передавать краткие признаки.
4. **Ограничение бюджета.** Добавить общий предел оборотов в существующий сервис, настроить существующий ToolCallLimitMiddleware, бюджет tool-output, отдельные output/reasoning-лимиты и concurrency на провайдера. Значения подобрать по качеству, не менять граф этапов без необходимости.
5. **Промпты и кеш.** Убрать измеренные дубли, сравнить компактные примеры, стабилизировать префиксы. Подтвердить cache hits и скидку. Только при доказанных повторах добавить точный result-cache на shared RedisCache.
6. **Дополнительные эксперименты.** Batch и Jev пробовать отдельно после первых результатов; не вносить сразу в основную цепочку. Сравнить цену успешного курса, а не только цену одного токена.

Каждый пункт — отдельный небольшой PR с собственными тестами и откатом. Этот документ не является разрешением на автоматическое внедрение всех предлагаемых вариантов.

## 9. Как проверить снижение расходов без ухудшения результата

### Метрики

- Стоимость одного успешного курса с включением расходов на неудачные прогоны; p50/p95 стоимости успешных курсов дополнительно.
- Input/cached/output/reasoning по stage/provider/model; отсутствующий usage отдельным счётчиком.
- Число provider attempts, chooser calls, tool-loop turns, critic/researcher calls, repair, повторно созданных блоков и изображений.
- Cache hit rate точных результатов и доля cached input провайдера — две разные метрики.
- Доля корректных структур без платного исправления, успешность полного курса, latency p50/p95, 429/timeout.
- Качество: покрытие учебных целей, фактическая корректность и источники, отсутствие дублирования блоков, валидность кода/Mermaid/формул, корректность quiz и соответствие ответа объяснению.
- RAG: доля непустых релевантных фрагментов, число внешних исследований после обращения к подготовленным материалам.

### Набор проверок

| Проверка | Что доказывает | Можно сейчас без оплаты |
| --- | --- | --- |
| Явная модель известного этапа | Chooser не вызван, правильная модель передана провайдеру | Да, mock clients |
| Компактный chooser | Base64/история отсутствуют, важные capabilities сохранены | Да |
| Parse/TypeAdapter/S3/SQL ошибка после ответа | Не происходит новый платный create при повторной локальной обработке | Да, счётчики mock create/save |
| 429/5xx/timeout | Ограниченные попытки, backoff; неопределённый timeout не объявлен бесплатным | Да, fake clock и mock transport |
| Инструмент возвращает ошибку много раз | Общий бюджет останавливает цикл независимо от успеха tools | Да |
| Один блок падает после готовности других | Готовые результаты используются при resume | Да; дополнительно integration с Redis/БД без LLM |
| RAG index → retrieve | Непустой нужный текст, source и course isolation | Да, unit mocks; локальный integration без генеративной LLM |
| Exact cache/single-flight | Одинаковая работа не оплачивается дважды; разные версии/курсы не смешиваются | Да |
| Сумма usage | Учитывает выборщик, все обороты и ответы перед parse failure без двойного учёта | Да |
| Цена и качество реального курса | Реальная экономия, эффект выбора моделей/промптов/лимитов | Нет: нужны реальные ответы и usage |

Для сравнения качества заранее зафиксировать одинаковые задачи: короткая и длинная тема, материалы преподавателя, отсутствие источников, сложный код, формулы, quiz, image-сценарий и длинное интервью. Использовать одинаковые входы, версии моделей и тарифов, сохранить baseline. Сравнивать изменения по одному; учесть стохастичность повторными прогонами. Предложение — начать с 20–30 парных курсов после согласования денежного бюджета; это план эксперимента, не выполненная проверка и не статистическая гарантия.

Критерии согласовать до эксперимента: допустимый процент снижения цены, отсутствие критических фактических ошибок, минимальный quality-score/доля прошедших рубрику, допустимая разница успешности и задержки. Простая валидность JSON или успешный мок не доказывает качество учебного материала.

## 10. Итог относительно ТЗ

Разобраны полный путь курса, LLM-точки, prompts, модели/провайдеры по конфигурации, инструменты, валидация и повторы. Подготовлены конкретные места изменения, статические подсчёты, сравнение оптимизаций, приоритеты и методика проверки денег и качества.

Не установлены фактические средние токены, частоты, выбранные модели и стоимость реального курса. Нельзя подтвердить денежную экономию или сохранение качества без real usage и результатов. По просьбе работать без трейсов в этих местах приведены формулы и условные сценарии, а не вымышленные замеры. Архитектуру и production-код в рамках анализа не меняли.
